# MCPオーケストレーション観点の論文書き換えテンプレ

本稿は、既存の「自己内省＋記憶DB＋サンドボックス適用」という枠組みを、**Model Context Protocol（MCP）時代のツールオーケストレーション**として再記述するための雛形です。  
**§8 に本研究採用の「MCP 3サーバー分解（改善版）」**、**§9 に検索拡張コンテキストの多ソース設計（改善版）**を固定した。実装は現行コードベースのままでも、卒論・論文では各節を**正アーキテクチャ／正の検索対象設計**として参照できる。

そのままコピーして、研究計画書・卒論・論文の該当節に貼り付け、固有名詞と数値だけ差し替えてください。

---

## 1. 位置づけ（1段落・要旨用）

本研究は、複数の外部ツール（LLM API、埋め込み、テスト実行、ファイル書き込み）を連鎖的に呼び出す**エージェント型オーケストレーション**において、実行時エラーに対する**安全な再計画（replan）と適用（apply）**を実現する枠組みを提案する。  
MCPの設計思想（ツール呼び出しの明示化・監査可能性・権限制御）に沿い、修正対象をホワイトリストで限定し、適用後に固定テストで検証し、失敗時はロールバックするという**制御ループ**を、リフレクション（仮説→修正→検証）とエピソード記憶（類似事例の再利用）で補強する。  
これにより、ツール連鎖が増えるほど顕在化しやすい**運用復旧コスト**を、人手デバッグに依存せず低減することを目的とする。

---

## 2. 研究課題の言い換え（問題設定）

- **従来**: 「LLMがコードを直す」という技術課題として記述しがち。
- **MCP文脈**: 「複数MCPサーバー／ツールを束ねるオーケストレーターが、失敗観測に応じて**どのツールを何回呼び、どこまで変更を許すか**を決める必要がある」という**制御問題**として記述する。

**テンプレ文**

> 本研究が扱うのは、単一のコード生成ではなく、ツール呼び出しの連鎖における**失敗回復のオーケストレーション**である。特に、本番適用に伴うリスク（破壊的変更・無限ループ・コスト逸脱）を抑えつつ、エラーに応じた再試行を自動化するため、安全ゲート（許可ファイル・テスト・ロールバック）と、失敗履歴を次の計画に反映するリフレクション、および類似事例を参照する記憶機構を統合する。

---

## 3. システム構成図のキャプション案

**図タイトル案**: MCPオーケストレーションに相当する制御ループ（観測→計画→適用→検証→記憶更新）

**キャプション案**

> オーケストレーターはエラーログと履歴に基づき修正案を生成し、ホワイトリスト内のファイルへの書き込みツール（apply）を介して変更を適用する。適用後は事前定義テスト（固定テストセット）で検証し、成功・失敗に応じてエピソード記憶を更新する。本実装ではDocker上の隔離環境で適用と検証を行い、失敗時はバックアップから復元する。

---

## 4. 貢献（箇条書き・MCP寄り）

そのまま論文の「貢献」節に使える形。

1. **ツール連鎖型エージェントにおける安全な適用制御**: 修正対象を明示的ホワイトリストで制限し、許可外への副作用を抑える設計を提示する。
2. **再計画ループの停止条件の明示**: 試行回数・時間・コスト（トークン）による停止を、オーケストレーションの**フェイルセーフ**として位置づける。
3. **記憶によるオーケストレーションの効率化**: 類似エラーに対する参照情報を、次回の計画（プロンプト）に注入し、試行回数やレイテンシの削減可能性を評価する。
4. **再現可能な評価プロトコル**: バグ注入・モック・固定テストによる自己循環問題への対処を、実験手順として固定する。

## 5. 評価指標のMCP的な言い換え

| 既存の言い方 | MCPオーケストレーション寄りの言い方 |
|--------------|-------------------------------------|
| 復旧成功率 | **オーケストレーション完了率**（所定のツール連鎖が「適用→検証成功」まで到達した割合） |
| 復旧レイテンシ | **回復までのウォールクロック時間**（計画・適用・検証を含む） |
| attempts | **再計画回数**（replan 回数） |
| tokens | **推論コスト**（オーケストレーションのコスト指標の一例） |

**注意**: 用語を置き換える場合は、本文で一度定義してから使う（「本稿では〜を復旧成功率と呼ぶ」）。

## 6. 限界・今後の課題（MCPと接続）

そのまま「限界」節に使える短い箇条書き。

- 本評価は特定スタック（FastAPI等）と固定シナリオに限定され、**多様なMCPサーバー構成**への一般化は未検証である。
- 実際のMCPエコシステムでは、ツールスキーマの変化・権限モデル・監査ログの標準化が課題であり、本枠組みの**ポリシー適合性**は今後の検証が必要である。
- 記憶DBの効果は条件により成功率差として現れない場合があり、**レイテンシ・再計画回数・ツール呼び出し回数**などの補助指標と併記することが望ましい。

## 7. 関連研究の書き方（1段落）

**テンプレ**

> 近年、エージェントは単一モデルではなく、検索・実行・ファイル操作などのツールを組み合わせてタスクを遂行する。MCPはそのようなツール連携を標準化する方向性の一つである。一方で、ツール連鎖が長くなるほど、失敗の局在化と安全な再試行設計が重要になる。本研究は、**失敗時の再計画と安全適用**に焦点を当て、記憶機構を加えたオーケストレーションの評価を行う。

## 8. 採用方針：MCP×本研究の接続（改善版・3サーバー分解）

### 8.1 位置づけ（一文）

**MCP は本研究の「ツール呼び出しを標準化するインターフェース層」**であり、**自己修復の方針・失敗履歴の組み立て・プロンプト合成・停止条件（試行／時間／トークン）はリフレクションエンジンおよびホスト側オーケストレーションが担う**。  
MCP クライアント（Claude Code、Cursor、自前ホスト等）が各サーバーのツールを呼び出すことで、「**自己修復エージェントが MCP プロトコル上で観測→記憶参照→安全適用→検証のループを回す**」という位置づけになる。

**補足（役割の重なり）**: 「次にどのツールを呼ぶか」の分岐も広義にはオーケストレーションである。論文では **（A）計画・内省・コスト制御＝リフレクション／ホスト**、**（B）副作用のある操作の経路＝MCP ツール** と書き分けると、クライアントの役割が過小にも過大にもならない。

### 8.2 サーバー① `observation_server`（観測）

当初案の `error_detection_server` を**観測一般**に拡張した名称とする（検出＝ログ取得に限定しない）。

| ツール | 入出力の要点 |
|--------|----------------|
| `get_error_log(scope)` | `scope` で対象実行（ジョブID・シナリオID・直近N行等）を指定。**スタックトレース／集約ログ**を返す。 |

**軽量運用（卒論の削り方）**: 初版では `sandbox_server.run_tests` の戻り値に**失敗ログ要約を含め**、`get_error_log` は後から追加する、またはホストがログを1回取得して `search_similar_errors` に渡す、と**2サーバー＋ホスト**に縮小してよい。

### 8.3 サーバー② `memory_server`（エピソード記憶）

Chroma 等への**読み書きを MCP ツールとして露出**する。

| ツール | 入出力の要点 |
|--------|----------------|
| `search_similar_errors(error_log, top_k?)` | 類似エピソードのリスト（類似度、過去の修正スニペット、成否メタデータ）。 |
| `save_episode(error_log, outcome, fix_snippet, scenario_meta)` | `outcome` ∈ {`success`, `failure`}。失敗は**負の知識**として保存可能。`scenario_meta` はシナリオID・試行回数など評価に必要な最小フィールド。 |

### 8.4 サーバー③ `sandbox_server`（隔離環境での適用・検証）

Docker 等の**隔離実行**と本研究の**安全ゲート**をここに集約する。

| ツール | 入出力の要点 |
|--------|----------------|
| `apply_allowed_fix(scenario_id, artifact)` | **許可パス（ホワイトリスト）内のみ**書き換え。`artifact` はパッチ相当またはシナリオごとに定義された入力形式。**バックアップ・ロールバック**は本ツールの契約内で保証する。 |
| `run_tests(scenario_id)` | 固定テストセットを実行し、**成功／失敗＋ログ要約**を返す（観測サーバーとログ経路を共有してよい）。 |

当初案の `apply_fix(code, scenario)` は、**許可範囲が名前に現れない**ため本採用では **`apply_allowed_fix`** に改称する。

### 8.5 典型フロー（論文用・箇条書き）

1. ホスト／クライアントが失敗を検知する（観測ツールまたは `run_tests` の結果）。
2. `search_similar_errors` で記憶を参照し、リフレクション用プロンプトに注入する。
3. LLM が修正案を生成する（**MCP 外**でもよいが、同一ホスト内と明記する）。
4. `apply_allowed_fix` → `run_tests` を順に呼ぶ。失敗ならバックアップ復元のうえ再ループ。成功なら `save_episode`。
5. 試行上限・時間・トークンでループを打ち切る（**リフレクション／ホストのフェイルセーフ**）。

### 8.6 現行コードベースとの対応（移行マップ）

| 現行 | 採用 MCP 側の帰属 |
|------|-------------------|
| `agent/reflection_engine.py` | クライアント／ホスト上の**内省・LLM 呼び出し・停止条件**（MCP ツールではない） |
| `agent/memory_db.py` | `memory_server` の実装コア |
| `evaluation/run_experiments.py` の適用・`predefined_tests` 等 | `sandbox_server` の実装コア |
| エラーログ文字列の組み立て | `observation_server` または `run_tests` 戻り＋ホスト |

**注意**: 現リポジトリは **MCP プロトコル未接続でも**上記と同じ責務分割で動いている。卒論では「**論理アーキテクチャを §8 に固定し、実装は HTTP／Python モジュールで検証**」と書いてよい。プロトタイプで **1 サーバーだけ MCP 化**しても採用方針と矛盾しない。

### 8.7 汎用性の主張（技術的裏付けの書き方）

- **シナリオID**と **`apply_allowed_fix` / `run_tests` の入出力スキーマ**を契約として固定すれば、**FastAPI＋React に限定しない**（別言語・別フレームのワーカーが同じ3ツールを実装する）主張が成り立つ。
- 強度を上げるには、**別スタックのミニシナリオ1本**で同契約を満たす実装または疑似コードを付録に置く。

### 8.8 限界（本節用の一文）

MCP は**権限モデル・承認 UI・サーバー間信頼**をすべて解決しない。本研究の**ホワイトリスト・固定テスト・ロールバック**は、MCP の上に載る**ポリシー**として明示する。

## 9. 採用方針：検索拡張コンテキスト（多ソース・過大な新語なし）

### 9.1 用語方針（本文での書き方）

新語を造らず、既存文献で通じる表現に寄せる。

- **多ソース検索**（multi-source retrieval）／**検索拡張生成（RAG）における複数コーパス**として記述する。
- ソースごとに取得件数や順序を変えることは、**選択的な検索結果の利用**や **selective retrieval** の文脈で説明可能である（**本稿独自の造語は用いない**）。

### 9.2 検索対象の四分類と優先度（採用）

「何を検索対象にするか」を次の四種に整理し、優先度を本文・表で明示する。

| 種別 | 検索対象 | 現状 | 追加コストの目安 | 優先度 |
|------|-----------|------|------------------|--------|
| ① | 過去の成功・失敗パターン（エピソード記憶） | 実装済み | — | **必須** |
| ② | 修正対象ファイルの**現在のコード**（許可パス内） | 未実装 | 低（読み込み＋索引化） | **高** |
| ③ | API ドキュメント（例：Gemini・FastAPI 仕様、PDF/HTML） | 未実装 | 中（取り込み・正規化） | **中** |
| ④ | 最近のエラー履歴（時系列ログのウィンドウ） | 未実装 | 低（ログ読み取り） | **中** |

**実装順の推奨**: ②は費用対効果が高く、既存ループへの追加が小さい。**①の上に②を載せる**と、類似事例だけでは足りない「局所コード文脈」を補える。

### 9.3 リフレクション用プロンプトへの埋め込み順（採用）

検索結果を次の**ブロック順**でプロンプトに載せる（見出しラベルは論文・実装で統一する）。

1. **修正対象コードの文脈**（②）
2. **過去の類似エラーに対する成功例**（①）
3. **過去の類似エラーに対する失敗例**（①、負の知識）
4. **発生したエラーログ**（観測そのもの）
5. **これまでの失敗履歴**（同一セッション内の試行要約）

②が未取得のときは省略し、①と④⑤のみで動作させる（**フォールバック**を一文で書く）。

### 9.4 実装スケッチの方向（参考・`memory_db` 周辺）

エピソード用コレクションとは別に、許可ファイルの内容を **別 Chroma コレクション**（例：`codebase`）に索引化し、エラーログをクエリとして `query` する想定とする。

- **チャンク化**: ファイル全文を1ドキュメントにしない。一定トークン幅または関数単位で分割し、メタデータに `filepath` とチャンク索引を持たせる（埋め込み長上限・検索精度の両面）。
- **パス**: Docker 内パスとホワイトリストを**一致**させる。索引対象は適用許可集合のみ。
- **更新**: 適用のたびにファイルが変わるため、**シナリオ開始時または適用直後**に該当チャンクのみ再索引する、`delete`→`add` 等の方針を固定する（古いチャンク残留を防ぐ）。
- **③外部ドキュメント**: ライセンス・秘匿情報の扱いを「限界」または「実験環境」に一文記載する。

### 9.5 論文での差別化の書き方（新語に頼らない）

貢献の置き所は次のようにする。

- 「単一コーパスの RAG」ではなく、**回復タスク向けにソース種別と優先度を設計した多ソース検索**であること。
- 成功・失敗のエピソード（①）と、**局所コード（②）**を併用することで、仕様変更（③）やログ（④）を足す余地を残していること。

## 10. 使い方メモ

- **卒論**: 第1章（背景）と第3章（提案）に「MCPオーケストレーション」用語を1〜2段落ずつ足すだけでも、文脈が一段引き上がる。
- **過剰にしない**: MCPを「製品名の羅列」にしない。あなたの実装が**何を制御しているか**（applyの範囲、テスト、停止条件、記憶）に結びつける。
- **採用アーキテクチャ**: MCP の分解は **§8**、検索拡張の多ソース設計は **§9** を参照元とする（図・表のキャプションも揃えると一貫する）。
